Campaign Daily Oversight — build spec

The daily tier of the PPC Oversight System, as a screen. One product, one marketplace, day grain. Sits alongside the existing Performance Monitor tables and reuses their arithmetic, their placement estimator and their attribution-settling treatment.

A) SCREEN LAYOUT

Top to bottom, one screen:

  • PINNED PRODUCT PROFILE — does not scroll away. Compact one row by default, click to expand.
  • SUB-TAB BAR — Ranking / Auto / Manual / Product & Category / SB / SD. Each label carries its own exception count, e.g. "Ranking (3)".
  • SUBTOTAL STRIP — this tab: spend, sales, ACoS, % of product ad spend.
  • LENS TOGGLES — Keywords / Placement / Target / Ranks. These sit INSIDE each tab, not beside it. They are different views of the same campaigns, not different campaign types.
  • TABLE — the shared column spine plus that tab's own columns.

Three rules that hold across the whole screen:

  • The profile is context, not content. Every ceiling, gate and diagnosis below it reads from the profile, so it stays pinned and nobody decides without it.
  • Profile figures stay product-total. They do NOT react to the selected sub-tab — if they did, TACoS and organic sales would stop being coherent. The subtotal strip carries the tab's own numbers.
  • Tabs are objective-led. Objective comes from targeting type by the standing rule (Exact = Ranking, auto and broad = Discovery, product/category = Profitable Conversion, brand keyword = Defensive). Where the two diverge, objective wins: a brand-defence Exact campaign is Defensive and is judged on defence, not on rank gap.

B) DATE RANGE

  • A from/to date range picker. NOT preset 1d / 7d / 30d buttons.
  • Presets cannot express "the three days around the deal" or "since the price change", which is what people actually need to look at.
  • Defaults to a SINGLE DAY. This is the daily tier and a bad yesterday is invisible inside a 30-day average. The current Performance Monitor defaults to 30d.
  • Show the selected span as a length badge — "1 day", "12 days" — so nobody misreads a wide range as a daily figure.
  • The 7-day rolling values stay beside the day figures regardless of the range chosen.

PRODUCT PROFILE — new pinned header block

Grain: one product x one marketplace. Everything here is product-level, not segment-level.

COMPACT STATE (pinned, always visible)

One row. Only what gates a decision:

  • Price + deal flag
  • Preferred variations — count live, and the lowest days cover among them
  • Advertised SKU right now
  • Break-even ACoS
  • Max allowable CPC
  • TACoS — day / 7-day rolling
  • Exceptions count

Everything else lives in the expanded state. A full profile block is 300-400px and would push the table off a laptop screen.

1) IDENTITY & ECONOMICS

  • Thumbnail, product title, parent ASIN, child ASIN, SKU, marketplace
  • Current price, and net price after any running deal
  • Our deal/promo status and type (Lightning / Best / Coupon / Promo), discount %, start-end date, live now Y/N
  • COGS / landed cost, and Amazon fees (referral + FBA)
  • Return rate — compute margin on NET units. Gross overstates it.
  • Contribution margin per unit, before ads
  • Break-even ACoS = contribution margin per unit / price. This is the ACoS at which CM2 = 0.
  • Target ACoS — the profit target, set below break-even by objective
  • Blended CVR — product, trailing 30 days
  • Break-even CPC at blended CVR = break-even ACoS x price x CVR
  • Max allowable CPC at blended CVR = target ACoS x price x CVR

NOTE ON THE CEILINGS: label both CPC figures "at blended CVR — per-keyword ceilings are on the rows". Recompute them whenever price or the deal changes. Price down pushes the ceiling down; deal-lifted CVR pushes it back up. The net effect must be computed, not assumed.

2) PREFERRED VARIATIONS

A table, not a single figure. Days cover is per child ASIN, so one product-level number hides the variation that is actually at risk.

One row per preferred variation:

  • Variation name
  • SKU
  • Advertised right now? Yes / No
  • Units on hand
  • Days cover
  • Inbound units
  • Next shipment ETA

Backup variations listed beneath, marked as backup.

NOTE ON DAYS COVER: read it against the next shipment ETA, never in isolation. 19 days cover with stock landing on day 12 is fine. 19 days cover with nothing booked is a gate on ranking spend.

3) THE DAY

Each figure with its 7-day rolling value beside it:

  • Total ad spend
  • Total ad sales
  • Total organic sales
  • Total sales
  • TACoS — day + 7-day rolling
  • Sessions
  • Unit session % (conversion)
  • Units ordered
  • Organic and ad sales %

NOTE ON TACOS — three things:

  • It belongs HERE, not in the segment tile row. There is no all-source sales figure per segment, so the empty segment tile is correct behaviour. Remove that tile or relabel it "product-level only" so it stops reading as broken.
  • The numerator is SP + SB + SD spend. SP alone against a total-sales denominator is not TACoS, and it drifts further the more SB and SD we run.
  • Daily TACoS is noisy — organic sales swing far more day to day than spend does. The 7-day rolling figure is the real number. The daily value is a pulse, never a trigger.

NOTE ON ATTRIBUTION: mark the last 3 days as still settling, the same treatment the chart already uses.

4) RANK & POSITION

  • BSR today, delta vs yesterday, 30-day sparkline
  • Category and subcategory BSR
  • Star rating + review count, delta vs yesterday
  • Our price rank out of the competitor set, e.g. "4 of 11"

5) COMPETITOR STRIP — top 10 ASINs

One compact cell per competitor, sorted by BSR:

  • ASIN + brand name
  • Price + delta vs yesterday
  • Deal running? type + %
  • BSR + delta vs yesterday
  • Rating / review count

RULES:

  • Highlight ONLY what changed since yesterday. Nobody will scan 40 static cells daily.
  • Add one derived summary line above the strip. This is the line people actually read: "2 competitors dropped price · 1 started a deal · our price rank 4 of 11"

6) TODAY'S EXCEPTIONS

  • Count plus severity chips for the daily checks D1-D7: ad eligibility, delivery stopped, stock cover, spend pacing, spend anomaly, budget cap time, runaway spend
  • Each one clicks through to the affected campaign or keyword

WHY THIS BLOCK EXISTS

The current window shows ad sales down 23.5% and orders down 21.0% while impressions are roughly flat. Nothing on the screen today can tell us whether that is bidding, price, stock or a competitor deal. This block answers it at a glance — and in the cases where it is not PPC, no bid change would have fixed it.

SHARED COLUMN SPINE

Every tab carries these columns, in this order.

Identity

  • Campaign
  • Effective state — derived: Live / Paused-KW / Paused-Campaign / Archived. A keyword is live only if BOTH the keyword state AND the campaign state are enabled. Show the raw values in the tooltip.
  • Objective — Ranking / Discovery / Profitable Conversion / Defensive
  • Portfolio
  • Advertised SKU

Levers

  • Bid
  • TOS modifier %, PDP modifier %, ROS modifier %
  • Effective bid per placement = base bid x (1 + modifier). This is context, not the judgement.
  • Budget
  • Spend as % of budget
  • In-budget % — how much of the day we served
  • Cap time — when it went dark. FLAG if capped before 18:00, or before 20:00 on a Ranking campaign.

Ceiling

  • Max allowable CPC for this row
  • CPC vs ceiling, split Total / TOS / PDP / ROS
  • Show as headroom: "$1.95 of $1.50 (130%)". Amber at 90-100%, red above 100%.

Performance — Total / TOS / PDP / ROS for each

  • Impressions
  • Clicks
  • Click share % — what proportion of clicks each placement took
  • CTR
  • CVR
  • CPC
  • Orders
  • Sales
  • ACoS

Row flags — colour the row, do not add columns

  • More than 1 enabled target in the campaign
  • Duplicate keyword
  • Budget capped early
  • Zero orders at 3x target CPA or more
  • ACoS above the SKU break-even on a Profitable Conversion campaign

TAB 1 — RANKING

Objective: Ranking. Exact keyword campaigns. This is the full tier; every other tab is a reduction of it. Brand-defence exact campaigns sit here under a Defensive chip and are judged on defence, not on rank gap.

Target composition

  • Primary target — the enabled target with the MOST CLICKS in the window. NOT the highest search volume. The row's ACoS, CVR, CPC and placement split are dominated by whichever target got the traffic, so labelling the row with a high-SV target that got 3 clicks makes every metric beside it describe a different keyword.
  • Primary target search volume
  • Number of enabled targets — FLAG RED if more than 1. The row expands to list every enabled target with its clicks and SV, so the rest can be paused.
  • Number of other campaigns targeting this same keyword — FLAG if more than 0
  • Duplicate group chip

Ranking commitment

  • Target rank
  • Current rank
  • CPR from Helium 10
  • DSTR from DataRova
  • Required sales, and actual sales
  • Required clicks, actual clicks, and the gap
  • Required impressions = required clicks / target CTR
  • Actual impressions, and the impression gap
  • 14 to 30 day organic rank strip, newest first

CTR and CVR — three values each

  • CTR: market (from SQP), target, actual, and the gap
  • CVR: market (from SQP), target, actual, and the gap

WHY THREE VALUES: the chain runs required sales, divided by CVR gives required clicks, divided by CTR gives required impressions, compared against what our TOS share can actually deliver. A CVR assumption is already inside Target Clicks ("at our own measured conversion") — this surfaces it, because when that assumption is wrong the required-clicks figure is wrong by the same factor, silently.

Constraint column — the only column that outputs a decision

Read in order. First match wins.

  • 1. Actual CVR below 60% of market CVR, verdict LISTING-CONSTRAINED. Hold the push, fix page / price / reviews, do not fund.
  • 2. Actual CTR below 60% of market CTR, verdict CREATIVE-CONSTRAINED. Main image, title, price, badge. Bids will not fix CTR.
  • 3. Impressions below required impressions, verdict IMPRESSION-CONSTRAINED. Raise the bid OR the TOS modifier. One, not both.
  • 4. Budget capped before 20:00, verdict BUDGET-CONSTRAINED. Raise budget or reallocate.
  • 5. Otherwise, verdict ON TRACK.

SUFFICIENCY: CVR needs at least 20 clicks and CTR needs at least 500 impressions before either can be read. Below that floor, show the target, grey the actual and set the constraint to OBSERVING. A "listing-constrained" verdict off 4 clicks sends someone to rewrite a listing that was never the problem.

CVR FLOOR IS A FUNDING GATE: below the rule-1 floor the campaign is not eligible for a bid or budget increase this cycle, regardless of rank gap. Rank follows sales velocity, so clicks that do not convert do not rank — they just spend the ranking budget.

SORT THIS TAB BY THE CONSTRAINT COLUMN, not by the rank gap. A campaign 40 clicks short because it is impression-constrained gets a bid change today. One 40 clicks short because CVR collapsed gets escalated to whoever owns the listing.

TAB 2 — AUTO

Objective: Discovery. There are no keywords here. The row is the campaign, expanding to its four auto target types — bids are set per target type, so that is the real grain underneath.

Per target type — close match, loose match, substitutes, complements

  • State
  • Bid
  • Impressions, clicks, CTR, CPC, orders, sales, ACoS

Discovery yield — judge auto on THIS, not on ACoS

  • New harvestable search terms found in the window
  • Cost per harvested term
  • % of spend going to terms already harvested elsewhere — this is leakage

Negative coverage

  • Number of negatives on the campaign
  • Are harvested terms negated back into this campaign? An auto campaign with no negatives leaks into its own exact campaigns.

DRILL: open the campaign to see the search terms it generated.

TAB 3 — MANUAL (BROAD / PHRASE)

Objective: Discovery. The row is the campaign, expanding to all targeted keywords.

  • Per keyword: keyword, search volume, state, bid, clicks, sales, ACoS
  • Same discovery yield block as Auto
  • Same negative coverage block as Auto
  • DRILL: search terms generated, per campaign

NOTE: Amazon Sponsored Products has Exact, Phrase and Broad only. There is no broad match modifier — that is a Google concept. Broad shaped by negatives is the negative-coverage column above.

AUTO AND MANUAL ARE NOT JUDGED ON ACOS. They are Discovery by definition. A broad campaign at 80% ACoS feeding three profitable exact campaigns is working. One at 30% ACoS producing no new harvestable terms is a dead end wearing a good number.

TAB 4 — PRODUCT & CATEGORY TARGETING

Objective: Profitable Conversion, or Defensive where the target is our own ASIN. The row is the campaign, expanding to each target.

This is separate from Manual because a PAT row targets an ASIN and a Category row targets a category node. Neither has a keyword, a search volume, a CPR or a rank, so they cannot share the Manual schema.

  • PAT target: ASIN plus the RESOLVED BRAND NAME plus product title. Never a bare ASIN.
  • Category target: category node plus refinements (price band, rating, brand)
  • State, bid, budget, cap time

Conquest context — joined from the Product Profile competitor set

  • Their price vs ours
  • Their BSR
  • Their rating
  • Deal running?

This is what decides whether a target is worth defending or dropping.

PLACEMENT NOTE: expect PDP-dominant placement here. FLAG a PAT campaign with a high TOS share — it usually means the target is behaving like a keyword campaign.

DRILL: which ASINs the ads actually served on.

TAB 5 — SPONSORED BRANDS

  • Ad format — Product Collection, Store Spotlight, Video
  • Landing page — Store vs custom URL
  • Headline and creative
  • NEW-TO-BRAND: NTB orders, NTB sales, NTB % of orders. This is what SB exists for — judging SB on ACoS alone misses the point entirely.
  • Top-of-search impression share
  • Viewable impressions

NOTE: SB placements differ from SP. Do not reuse the TOS / PDP / ROS block as-is.

TAB 6 — SPONSORED DISPLAY

  • Targeting — contextual (product / category) vs audience (views remarketing, purchases remarketing, similar-to)
  • Cost type — CPC vs vCPM. These are NOT comparable. Never sum them.
  • Viewable impressions
  • vCPM
  • View-through conversions
  • NTB
  • On-Amazon vs off-Amazon split

NOTE: the existing OFF-AMZ column reads 0 on every SP row because Sponsored Products does not serve off-Amazon. It is not "too sparse to rate" — it is structurally empty on SP, and belongs on this tab.

DUPLICATE KEYWORD DETECTION

WHY: Amazon exact match already serves close variants — plurals, misspellings, stemming, function words. Two targets that normalise to the same key are bidding in the SAME auction. We are outbidding ourselves.

The match key

Match key = normalised keyword + match type. To normalise:

  • Lowercase
  • Strip punctuation — hyphens, apostrophes, commas, slashes
  • Drop stopwords: a, an, the, for, of, with, and, or, in, on, to, by
  • Singularise each token

Singularise carefully — this is not a trailing-s strip

  • Ends in ss, us or is — leave unchanged. Mattress, status, analysis.
  • Ends in ies — becomes y. Canopies becomes canopy.
  • Ends in es after s, x, z, ch or sh — drop the es. Boxes becomes box.
  • Otherwise ends in s — drop the s. Sheets becomes sheet.
  • Plus an irregulars list.

A naive trailing-s strip turns "mattress" into "mattres" and the team stops trusting the flag entirely.

Three cases

  • TIER 1 — same key, same word order, SAME match type. This is real self-competition. Filled cell wash plus a solid rail. Keep one instance, pause the rest.
  • TIER 2 — matches only after sorting the tokens, so the word order differs. Lower confidence. No fill, dashed rail, same hue. A human confirms before acting.
  • CROSS-MATCH-TYPE — same key, DIFFERENT match type. This is intended Hero/Halo layering, NOT a defect. Do not shade it. Show a link icon and count instead, and check that an isolation negative exists for that exact term in the broader campaign. Flag if it does not.

Shading — one keyword, one shade

  • WHERE: the keyword cell background plus a 3px left rail. NOT the whole row — the row already carries the rank heatmap, the placement purples, crawl markers and low-click greying, and a full-width wash fights all of them.
  • SLOT: slot = hash of the NORMALISED key, mod 8. Hashing the normalised key means plural and singular land on the same shade. Hash-based rather than row-order-based means the shade is stable across the keyword view, the campaign view and future sessions.
  • PALETTE: 8 hues. No red, which reads as an error, and no green, which is already the rank heatmap. Use amber, orange, rose, magenta, violet, indigo, cyan, teal. Keep the wash very light and the rail saturated. Check violet and indigo against the placement-estimate purple before shipping.
  • CHIP: a group ID in the keyword cell — D1, D2, D3. The chip is the identifier and the shade is only a scanning aid, so the signal still works in greyscale, for colourblind viewers, and when two unrelated groups land on the same slot. Click the chip to filter the table to that group.
  • KEEP / PAUSE: within each Tier 1 group, mark one row KEEP — the one with the most clicks, or on a tie the one in the Ranking-objective campaign — and mark the rest PAUSE.
  • Store the normalised key as a hidden sortable column so duplicate rows can be sorted adjacent.

ECONOMIC CEILINGS

Max allowable CPC = target ACoS x price x CVR.

CVR is inside that formula, and CVR varies per keyword. A keyword converting at 25% justifies roughly double the CPC of one converting at 12% on the same product. So the profile carries a reference ceiling at blended CVR, and each row carries its own ceiling at its own CVR.

Which CVR to use on a row

  • 20 clicks or more in the window — use the row's own measured CVR
  • Below that — use the SQP market CVR, and mark the cell as estimated
  • Never use a blended product CVR on an individual row

Multi-SKU campaigns

  • If a campaign has product ads for more than one SKU, use the LOWEST ceiling across them and flag the row. One bid serves all of them, so the thinnest-margin SKU sets the limit.

The decision this drives

  • Over ceiling on TOS only, under on PDP and ROS — cut the TOS MODIFIER. Not the base bid, which would discard the profitable PDP and ROS traffic.
  • Over ceiling on every placement — cut the BASE BID.
  • Under ceiling everywhere but under-delivering — headroom exists. Raise the bid OR the modifier. One, not both.

Objective gating — the one place where acting on the number in front of you is wrong

  • Profitable Conversion and Defensive — ENFORCE the ceiling.
  • Discovery (auto, broad, phrase) — advisory only. Judge on discovery yield instead.
  • Ranking — DO NOT ENFORCE. Running above break-even is the entire point of a ranking push. The constraint there is the ranking budget and the CVR gate, not ACoS. Enforcing the ceiling on this tab will kill working pushes.

DATA INTEGRITY RULES

These apply to every tab and are not optional.

Attribution settling

  • Mark the last 3 days as still settling, the same treatment the chart already uses.
  • NO DELTAS INSIDE THE SETTLING WINDOW. A conversion delta there compares a settled number against one still arriving, so it always reads as a decline and will manufacture a fake drop every single morning.

Delta baselines — pick the right one per metric

  • Vs yesterday — competitor price, deal on/off, BSR, rating. Things that genuinely move overnight.
  • Vs 7-day mean — spend, CPC, sessions. One day alone is noise. This is what the D5 anomaly check already uses.
  • Vs target — rank. The useful delta is distance to the committed target rank, not yesterday's wobble.

A naive "vs yesterday" on everything makes the noisy metrics scream constantly, and then people stop looking.

Sufficiency floors

  • CVR needs 20 clicks or more
  • CTR needs 500 impressions or more
  • Bid decisions need 10 clicks or more
  • Below the floor the answer is "observing", which is a logged decision, not silence.

Data vintage

  • The rank-crawl staleness banner is exactly the right instinct. Extend it.
  • Required-clicks blends a rank up to 5 days old, weekly SQP, a monthly Helium 10 CPR and a measured CVR. Stamp the composite age on the derived column, not only on the crawl.

Estimate coverage

  • Per-cell placement coverage already exists in a tooltip. Surface a per-row indicator as well.
  • Hover-only disclosure means people read estimates as measurements, and a 32%-covered row currently looks identical to a 95%-covered one.

OPEN ITEMS

  • 1. COMPOSITE DATA VINTAGE on required-clicks and the CPR / DSTR columns.
  • 2. COMPETITOR DATA SOURCE. Daily price, BSR and deal state for 10 ASINs per product is a real pipeline — Keepa, DataDive or Helium 10. This is the most-specified and least-sourced part of the profile.
  • 3. TACOS NUMERATOR. Confirm it carries SP + SB + SD spend, not SP alone.
  • 4. OFF-AMZ COLUMN. It reads 0 on every SP row. Confirm it moves to the SD tab.
  • 5. EXCEPTION ENGINE. Confirm D1-D7 actually fire against the thresholds config and produce a queue, rather than the counts being read off columns by eye.
  • 6. ACTION-LOG GRADING. Confirm something reads the log back and scores actions worked / flat / backfired two cycles later. Without that the log is a diary, and the weekly execution-verification step has no input.

Where the standing SOPs disagree with this spec on a threshold, a definition or a lever, THE SOPs WIN.
